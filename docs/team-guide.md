# 팀 공유 안내

## 5분 안에 이해하기

이 프로젝트는 **공공데이터를 찾고 연결하는 지도**를 만든다. 포털 주소만 모으는 디렉터리에서 더 나아가 ‘무엇을 측정하는 자료인지’, ‘어떤 맥락에서 함께 찾는지’, ‘왜 추천하는지’를 구조화한다.

AI는 질문을 개념으로 해석하고 설명하는 교체 가능한 구성 요소다. 팀이 직접 축적하는 핵심 자산은 검토된 개념·자료 대응과 근거가 있는 관계 DB다. 모든 공공데이터의 모든 칼럼을 먼저 내려받아 서로 비교해야 시작할 수 있는 구조는 아니다.

| 용어 | 이 프로젝트에서의 의미 |
|---|---|
| Ontology / 온톨로지 | 개념·지표·자료·기관의 종류와 연결 규칙을 정의한 설계 |
| Knowledge Graph / 지식그래프 | 설계에 실제 개체와 근거가 있는 관계를 채운 결과 |
| Metadata / 메타데이터 | 제공기관, 측정 대상, 시간·공간 단위, 스키마, 출처, 이용 조건 같은 자료 설명 |
| Concept / 개념 | 인구이동·고용·주거처럼 탐색의 의미 단위 |
| Indicator / 지표 | 순이동·청년 실업률처럼 무엇을 어떻게 측정하는지 정의한 항목 |
| Dataset / 데이터셋 | 특정 통계표·파일·API 등 실제 자료 단위. 포털 자체와 구분 |
| Provenance / 근거·출처 | 관계를 판단한 공식 문서·관찰·검토 기록과 확인 시점 |
| Harness / 실행 제어 | 탐색 깊이·횟수·시간·비용·자원 사용과 이용 조건을 통제하는 규칙 |
| Agent | 모델과 도구 호출을 연결해 작업을 진행하는 실행 로직. LLM 모델 자체와 구분 |

## 그래프를 보는 순서

1. 저장소의 공유 브랜치에서 **Code → Download ZIP**으로 내려받고 압축을 푼다.
2. [ontology-explorer.html](ontology-explorer.html)을 Chrome 또는 Edge로 연다. GitHub 파일 화면에서는 코드가 표시된다.
3. ‘청년 인구 유출’ 질문에서 깊이를 1과 2로 바꿔 직접 자료와 확장 후보를 비교한다.
4. 자료 노드를 선택해 추천 경로·출처·미확인 조건을 확인한다.
5. ‘서비스·Harness 구조’ 탭으로 이동해 서버와 외부 LLM의 역할을 확인한다. 이 탭은 설계 구조이며 서버가 실행 중이라는 뜻은 아니다.

화면의 질문은 3개 고정 예시다. 점선 관계는 검토가 필요한 후보이며, 그래프 가까이에 있다는 이유만으로 통계적 상관이나 결합 가능성을 의미하지 않는다.

양식은 공통 구조 참고용이며, 현재 모든 양식을 자동 적재하는 수집 파이프라인이 구현된 것은 아니다. `model.json`과 RDF·예시 결과는 생성 파일이다. 변경 시 `build_model.py`와 근거 기록을 수정한 뒤 README의 재생성 명령을 실행한다.

## 관계를 세 종류로 구분하기

**의미 관계:** ‘실업률은 고용 상태를 설명하는 지표다’처럼 개념 정의에 근거한 연결이다. 용어집·공식 지표 설명이 근거가 된다.

**결합 후보:** 두 자료가 같은 지역 코드·기간·대상을 공유하는지 검토할 연결이다. 같은 ‘서울’ 또는 ‘청년’이라는 이름만으로 결합을 허용하지 않는다. 행정구역 변경, 연령 범위, 빈도, 단위, 이용 조건 등을 먼저 맞춘다.

**통계적 관계:** 실제 관측값을 결합하고 계산한 결과다. 변수, 표본 수, 기간·지역, 전처리, 분석 방법, 계수와 불확실성, 실행 코드와 출처를 남겨야 한다. 현재 저장소에는 이런 분석 결과가 없다. 청년 유출과 고용·주거의 연결은 탐색 가설이다.

## 다음 개발 단위

1. 국내외 제공처 목록을 지속적으로 보완하고 중복·운영 주체·접근 상태를 검토한다.
2. 분야별 메타데이터 수집기를 추가하고 공통 단위·코드·지표 정의를 정규화한다.
3. 선택한 질문에서 필요한 자료의 스키마와 실제 계열을 확인해 결합 후보를 검증한다.
4. 검증된 관계를 PostgreSQL 등 운영 저장소에 적재하고 동일한 탐색 상한을 구현한다.
5. 제한된 외부 LLM 질의 해석, 이용 조건 검사, 영속 감사 기록을 연결한다.

전 분야를 수용하는 설계와 전체 자료의 수집 완료는 다르다. 새 분야를 추가할 때는 핵심 구조를 재작성하기보다 개념·지표·자료·관계·근거를 확장한다.

## GitHub에서 협업하기

현재 공유 내용은 `codex/ontology-sharing-20260912` 브랜치에 있다. 팀에는 이 브랜치의 링크를 공유한다.

```bash
git clone --branch codex/ontology-sharing-20260912 --single-branch https://github.com/chlsuun/public-data-ontology.git
cd public-data-ontology
```

Public 저장소는 로그인·초대 없이 열람하고 내려받을 수 있다. 링크를 받은 사람 외에도 검색으로 접근할 수 있다. 코드를 직접 수정하는 권한은 별도로 관리한다.

비공개로 운영할 때는 등록된 협업자만 접근할 수 있다. 저장소 소유자가 **Settings → Collaborators**에서 팀원의 GitHub 계정을 추가하고 팀원이 초대를 수락하면 된다. 팀원 초대와 기본 브랜치 병합은 별도 작업이다.

검토 시 각 관계에 대해 ‘출처가 있는가’, ‘확정·후보가 구분되는가’, ‘같은 단위로 연결할 수 있는가’를 확인하고, 변경은 별도 브랜치에서 진행한다.

## 공유 링크에 404가 표시될 때

GitHub는 비공개 저장소에 접근 권한이 없는 경우에도 404를 표시할 수 있다. 파일이 지워졌거나 업로드가 실패했다는 뜻으로 단정하지 않는다.

- **Chrome과 앱 내 브라우저는 로그인 상태가 별개다.** Chrome에서 저장소가 열려도 앱 내 브라우저에 `Sign in`이 보이면 그 브라우저에서는 로그인되지 않은 상태다.
- 비공개로 운영할 때는 해당 브라우저에서 저장소 소유자 또는 초대를 수락한 팀원 계정으로 로그인한다.
- 로그인 없이 링크만으로 공유하려면 저장소 공개 범위를 Public으로 설정해야 한다. 이 경우 코드·설계서·조사 자료와 커밋 기록을 누구나 볼 수 있다.
- 같은 비공개 저장소에 파일을 재업로드하거나 브랜치를 새로 만들어도 접근 권한 문제는 해결되지 않는다.

공유할 주소는 [현재 작업 브랜치](https://github.com/chlsuun/public-data-ontology/tree/codex/ontology-sharing-20260912)다. 저장소 기본 화면과 다른 브랜치이므로 이 주소를 사용한다.
